# The PII gate — what it refuses, how to turn it on, what it cannot see

TASK-938, 2026-10-02. `scripts/pii_gate.py`,
`tests/test_a_gate_refuses_a_real_identity_before_the_commit.py`,
`config/pii-gate-exceptions.txt`.

## IT IS NOT ON UNTIL SOMEBODY RUNS ONE COMMAND

    py -3 scripts/pii_gate.py --install

`.git/hooks` is not tracked and not cloned, so this is needed once per checkout —
and because this repository sets `core.hooksPath` in its LOCAL config, the
installer reads that config rather than assuming `.git/hooks`. The directory is
**shared by every worktree**, so one install covers every agent worktree at once,
and so does one uninstall. Deliberately left UNINSTALLED when it was written: a
control with that blast radius across concurrent sessions is the operator's
switch to throw, not a side effect of a merge.

Verify it is live by making a commit and looking for a `PII-GATE:` line.

## WHAT IT REFUSES

A commit whose **added lines** or whose **commit message** carry a real identity.
Four layers:

| layer | source | catches |
|---|---|---|
| CORPUS | fingerprints built live from `work/queue.jsonl`, `candidates.jsonl`, `campaigns.jsonl`, `reply-drafts.jsonl`, `agency-dnc.jsonl` | company names, domains, record ids, full contact names, contact keys, addresses, LinkedIn handles — **including the ones nobody remembered to list** |
| DENYLIST | `FORBIDDEN_DOMAINS` / `FORBIDDEN_NAMES` / `FORBIDDEN_FIGURES`, IMPORTED from `tests/test_fixture_hygiene.py`, never copied | the short, common-word identities the corpus layer drops on purpose, each already human-reviewed |
| STRUCTURAL | no list at all | an email on a domain that can resolve, a phone outside the reserved-fiction set, a `linkedin.com/in/<handle>` that is not a known invention |
| EXCEPTIONS | `config/pii-gate-exceptions.txt` | nothing — it is how a false positive is cleared |

One identity has **one fingerprint across every shape it arrives in**:
`a-b-c.example`, `a-b-c-example`, `A B C Example` and `a.b@c` all canonicalise to
the same string, so a corpus that holds only the domain still refuses a fixture
that writes the name. Diacritics are folded, so the accented spelling in the
corpus catches the unaccented one in a fixture.

## HOW TO CLEAR A FALSE POSITIVE

The refusal prints a `pg-` fingerprint beside every hit. Add one line per hit:

    <path-glob> | <pg- token> | <your name> | <why, 12+ characters>

`rule:structural:phone` in the token field clears a whole rule on that path. The
**token, never the value** — the file is tracked, and the gate refuses an entry
whose token is not a fingerprint or a rule. A malformed line **refuses the
commit** rather than being skipped: "my exception did not parse and the gate said
PASS" is the worst outcome available.

## WHAT IT CANNOT CATCH

- `git commit --no-verify`, and `git push`. Hooks are advisory by construction.
  Nothing in git can change that; using it here is a reportable decision.
- An identity that is **not in the corpus files it reads and not on the
  denylist** — a name typed from memory, or one that only exists in a provider
  dashboard. The structural rules are the backstop and they only cover addresses,
  phones and LinkedIn handles.
- Anything **already committed**. This is a pre-commit control, not a history
  scan. `scripts/history_pii_scan.py` answers the history question.
- A real token that has already spread to **25 or more tracked files**: document
  frequency is how the gate tells English from identities, and it counts the
  leaks too. The denylist layer is unconditional for exactly this reason.
- A **bare given name** or a company name under six characters. Deliberate: at
  that length the corpus layer fires on prose. Those live on the hand-reviewed
  denylist.
- A commit made **on a branch that does not carry the script**. The hook warns
  `PII gate NOT RUN` and allows the commit, because the alternative is making
  every older branch uncommittable.

## THE CORPUS IS GITIGNORED AND THAT IS A TRAP, NOT A DETAIL

`work/` is gitignored, so `git grep` and every tool honouring `.gitignore` match
**nothing** there. A "no PII found" search over it is not a measurement. The gate
opens the files itself; the test proves `git grep` finds the planted identity
nowhere in its fixture repository and the commit is refused anyway.

The gate never writes a corpus value anywhere tracked. The matcher is a set of
salted fingerprints, the on-disk cache is fingerprints only and lives in the
gitignored `cache/` tree (never in `work/` — a tool that protects the corpus has
no business writing into it), and an exception names a fingerprint. The salt is
public, as in `scripts/task189_scrub_pii.py`: a fingerprint is a stable NAME an
operator can paste into an issue, not a cipher.
