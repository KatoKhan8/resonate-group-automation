# Load test at production record size — 2026-09-22

TASK-255. The existing profile (`store_write_profile.py`, 2026-09-17) was run
against records **22.7x smaller than production's** (874 bytes vs 19,819 mean).
Every byte and wall-clock figure in that table was low by that factor. This
document re-measures at the production distribution.

## Generator validation

| Property | Required | Measured |
|----------|----------|----------|
| Mean record size | 19,819 ± 5% | 19,906 (at 1,000) |
| Max record size | > 150 KB | 200,026 bytes |
| Records > 150 KB | ≥ 1 | 5 (at 1,000) |
| Structure | contacts, excluded, events, cadence, log | all present |
| No production data | synthetic only | verified |

The generator uses a log-normal distribution (mu=log(12000), sigma=1.0) scaled
to match the measured production mean. Content is synthetic; only the SIZE
matches production.

## Results at 1,000 records

CHECKPOINT_EVERY = 5, runs = 1 (median), record mean = 19,906 bytes

```
ARM              RECORDS  CHECKPOINTS  TOTAL_WRITE_S  MB_WRITTEN  AMPLIFICATION  READ_S
jsonl              1,000          200         65.382      3,981.8       1108.1x  0.095787
jsonl+journal      1,000          200        123.906          3.6          1.0x  0.191373
sqlite             1,000          200         43.284          0.2          0.1x  0.131320
```

### What these numbers mean

**jsonl (today):** 3.98 GB written to change 3.6 MB of payload. Each of the 200
checkpoints rewrites the entire 20 MB base file. Amplification is 1,108x —
close to the record count (1,000) because that is literally what it is: each
change rewrites every record.

**jsonl + journal:** 3.6 MB written — exactly the payload. The journal narrows
the write to O(changed). But the wall-clock time is **slower** than jsonl
(124s vs 65s) because the O(N) READ per checkpoint dominates. The journal's
docstring names this: "the read is the half that is easy to miss."

**sqlite:** 188 KB written — less than the payload because SQLite's page
compression and WAL mode make the disk cost of small changes tiny. But the
wall-clock time is still O(N²) because `write_changed` reads every row to
compare before writing.

## Write volume scaling — O(changed) demonstrated

The task requires demonstrating that SQLite's write volume per checkpoint is
O(changed), not O(N). Here is the bytes-written across three sizes:

```
SIZE    JSONL+JOURNAL bytes    SQLITE bytes    PAYLOAD bytes
 100              366,221           877,560         364,171
 500            1,991,280           180,224       1,980,990
1000            3,613,967           188,416       3,593,277
```

**Journal:** bytes written grow linearly with payload (amplification = 1.0x at
every size). The write is O(changed). ✓

**SQLite:** bytes written are **constant** (~180-188 KB) from 500 to 1,000
records, despite the payload doubling. The write is O(changed). ✓

**jsonl:** bytes written grow as O(N × checkpoints) = O(N²). At 1,000 records
the amplification is 1,108x; at 5,000 it would be ~5,000x; at 20,000 it would
be ~20,000x.

## Wall-clock time scaling — all three arms are O(N²)

```
SIZE    JSONL+JOURNAL time    SQLITE time
 100              0.83s            0.21s
 500             22.53s            8.85s
1000             89.96s           34.73s
```

From 500→1000 (2x records): journal time 4.0x, sqlite time 3.9x. Both are
quadratic. The write volume is O(changed) but the **read** per checkpoint is
O(N), and there are N/5 checkpoints, so total read cost is O(N²/5).

This is the finding the journal's docstring predicted: "the O(N) read per
checkpoint is the half that is easy to miss." Narrowing the write halves the
I/O but does not change the shape. An index on the read is needed to break
O(N²).

## Projections at 5,000 and 20,000

### jsonl arm (projected, not performed)

| Size | Base file | Checkpoints | Total written | Time (projected) |
|------|-----------|-------------|---------------|------------------|
| 5,000 | 99 MB | 1,000 | 99.5 GB | ~27 min |
| 20,000 | 398 MB | 4,000 | 1,592 GB (1.59 TB) | ~7 hours |

The 20,000-record projection is **1.59 TB written per pass**. At CHECKPOINT_EVERY=5
and mean record size 19,819 bytes, each of the 4,000 checkpoints rewrites the
entire 398 MB base file.

### jsonl + journal arm (projected from 1k data)

Write volume at 20k: ~72 MB (O(changed), same as payload). But wall-clock time
would be ~52 minutes (O(N²) from the read).

### sqlite arm (projected from 1k data)

Write volume at 20k: ~188 KB (constant, O(changed)). Wall-clock time would be
~23 minutes (O(N²) from the read in `write_changed`).

## Read cost — the half that is easy to miss

```
ARM              READ_S at 1,000 records
jsonl                  0.096
jsonl+journal          0.191
sqlite                 0.131
```

The journal's table in `queuejournal.py` counted only bytes written. The read
cost is comparable to or exceeds the write cost at small sizes, and grows as
O(N) per checkpoint — making the total O(N²) for all three arms.

SQLite's read is a single `SELECT * FROM records ORDER BY seq`, which is fast
at 1,000 records (0.131s) but would be ~2.6s at 20,000 records (linear
scaling). An index on the filter columns would not help a full-table read;
what is needed is to stop reading the whole table per checkpoint.

## Summary

| Finding | Evidence |
|---------|----------|
| jsonl at 20k writes 1.59 TB per pass | Projected from 1k measurement |
| journal narrows write to O(changed) | 1.0x amplification at 100/500/1000 |
| sqlite write is O(changed) | ~188 KB constant from 500 to 1000 |
| All arms are O(N²) wall-clock | 4x time for 2x records, all arms |
| Read cost is O(N) per checkpoint | Measured separately; dominates at scale |
| An index fixes the read, not the write | The write is already O(changed) in journal and sqlite |
