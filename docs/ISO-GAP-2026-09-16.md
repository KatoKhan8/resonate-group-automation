# ISO-GAP-2026-09-16: completing the ISO 3166-1 alpha-2 lookup

TASK-201. The `ISO_TO_NAME` table in `src/icpstructural.py` held 34 codes
(including the `UK` alias for `GB`). 17 codes that appear in real office data
were absent, affecting 21 records. An office in those countries did not resolve
to a country at all, because the code was not in the table.

## What a missing code caused and where

`resolve_country(rec, segment)` at `src/icpstructural.py:246` checks three
witnesses in order:

1. `segment.country` - a pre-resolved country name
2. `segment.country_code` mapped through `ISO_TO_NAME`
3. The trailing token of each `company_facts.offices` line, mapped through
   `ISO_TO_NAME`

When a code is absent from `ISO_TO_NAME`, witnesses 2 and 3 silently return
nothing. The function falls through to the next witness or returns `(None, None)`.
The caller `_geography()` then sees no country and returns UNKNOWN with the
message "no usable location evidence anywhere on the record" - which is false:
the record has an office in Czechia, but the system cannot say so.

The only caller of `resolve_country` is `_geography()`, which is called by
`structural()` - the public entry point consumed by the ICP pipeline.

## The fix

Replaced the 34-entry table with the complete ISO 3166-1 alpha-2 set: 249
officially assigned codes plus the exceptionally reserved `UK` alias for `GB`.

Source: ISO 3166 Maintenance Agency, ISO Online Browsing Platform
(https://www.iso.org/obp/ui/#search/code-list/code_iso3166-1-alpha-2).

The table is now ordered alphabetically by code for maintainability. A future
code addition is a one-line diff, not a forensic exercise.

## Do any resolve onto the include list?

Two records PASS geography: `7ea8b6c1c25f` (United States) and `39ce634c18a4`
(Spain). However, both resolve through `segment.country`, not through the fixed
ISO table. Their office data contained a previously-missing code, but the
segment already carried the country name, so their verdict was PASS before the
fix and remains PASS after it.

**The ISO table fix changed zero verdicts.** The 19 records that remain UNKNOWN
are now *informed* unknowns - the system can say "this company's office is in
Ukraine" rather than "we could not tell where this company is". Those are
different facts, and one of them was false.

No record was recovered for free. None of the 17 previously-missing codes
resolve to a country on the client's include list.

## What was not changed

- The include list is untouched.
- The exclude list is untouched.
- The UNKNOWN-versus-FAIL rule is untouched: an off-list country still returns
  UNKNOWN, not FAIL. TASK-193 established this as deliberate.
- No record moved between states.

## The coverage test

`tests/test_iso_coverage.py` verifies four things:

1. The table covers all 249 ISO 3166-1 alpha-2 codes.
2. The `UK` alias for `GB` is present.
3. Every two-letter trailing token in any record's office data resolves to a
   country. This is the test that would have caught the 17 missing codes.
4. No entry maps to an empty country name.

Break-the-wiring verified: removing `CZ` from the table causes test 3 to fail
with `['CZ']`.
