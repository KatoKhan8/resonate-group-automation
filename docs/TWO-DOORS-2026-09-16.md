# TWO-DOORS-2026-09-16

TASK-198. `providerwrites.SUPPORTED` is described everywhere as the complete
write surface. It is not. Four EmailBison writes bypass `providerwrites.perform`
and call the provider transport directly from `bisonfactory`. HeyReach has no
such calls; every HeyReach write goes through `perform`.

## The enumeration

### EmailBison — through `providerwrites.perform`

| Transport call         | Operation constant       | In SUPPORTED | Prospect-facing |
|------------------------|--------------------------|--------------|-----------------|
| `bison.create_campaign`| `EMAIL_CREATE_CAMPAIGN`  | yes          | no              |
| `bison.set_sequence`   | `EMAIL_SET_SEQUENCE`     | yes          | no              |

### EmailBison — direct (bypassing `perform`)

| Transport call              | Operation constant      | In SUPPORTED | Gates that actually apply                                |
|-----------------------------|-------------------------|--------------|----------------------------------------------------------|
| `bison.set_limits`          | `EMAIL_SET_LIMITS`      | no           | daily volume must be declared; runs before leads attach  |
| `bison.set_schedule`        | (none defined)          | n/a          | sending window must name days, start, end, timezone      |
| `bison.attach_senders`      | `EMAIL_ASSIGN_SENDER`   | no           | senders must be named in campaign row                    |
| `bison.ensure_custom_variables` | (none defined)      | n/a          | idempotent; declares workspace variables, no leads       |
| `bison.create_lead`         | `EMAIL_ADD_LEAD`        | yes          | killswitch, collision, unsupported claims, greetings, missing copy, pre-attach status re-read |
| `bison.attach_leads`        | `EMAIL_ADD_LEAD`        | yes          | same as `create_lead`; campaign must be stopped          |
| `bison.update_lead`         | (none defined)          | n/a          | reconciles stale variables on existing leads only        |
| `bison.pause_campaign`      | `EMAIL_PAUSE`           | yes          | refuses a campaign not previously active                 |

### HeyReach — through `providerwrites.perform`

| Transport call                  | Operation constant       | In SUPPORTED | Prospect-facing |
|---------------------------------|--------------------------|--------------|-----------------|
| `heyreach.set_sequence`         | `LINKEDIN_SET_SEQUENCE`  | yes          | no              |
| `heyreach.add_leads_to_campaign`| `LINKEDIN_ADD_LEAD`      | yes (cond.)  | yes             |

### HeyReach — direct (bypassing `perform`)

None. Every HeyReach factory write goes through `providerwrites.perform`.

## Recommendation: (b) — leave the calls, correct the documentation

Two honest options were on the table:

**(a)** Route the four through `perform`, so `SUPPORTED` means what it says.
**(b)** Leave the calls, make `providerwrites` state plainly that it is not the
complete surface, with a pointer to the factory gates.

### Why (b)

1. **Option (a) requires adding to `SUPPORTED`.** `EMAIL_SET_LIMITS` and
   `EMAIL_ASSIGN_SENDER` are in `OPERATIONS` but not in `SUPPORTED`. `perform`
   calls `require_supported` as its first gate, so routing these through
   `perform` requires adding them to `SUPPORTED` first. Adding to `SUPPORTED`
   is an operator authorization decision; TASK-198 explicitly may not make it.

2. **`create_lead` and `attach_leads` would need an `Authorization`.**
   `EMAIL_ADD_LEAD` is prospect-facing. `perform` demands an
   `executionguard.Authorization` for prospect-facing operations, which
   requires a sealed `Readback` from `configdiff.compare_bison()`. The staging
   path does not currently produce one. Building the authorization machinery
   for staging is a real behaviour change that could refuse work that
   currently succeeds, and the task says not to change what `stage()` does in
   the success path without saying so explicitly.

3. **The factory gates are real.** They were added after measured incidents:
   nineteen contacts staged into campaign 481 with nine already in the
   client's own campaigns produced the collision check; the killswitch check
   closes the tenant-level gap; the pre-attach status re-read catches a
   campaign resumed by hand between the stop and the attach. Routing through
   `perform` would add `perform`'s gates on top, and the task says
   duplication is the correct outcome — but the factory gates would still
   need to remain, so the net effect is more code running twice rather than
   one door.

4. **The defect is enumeration, not gating.** The problem TASK-198 names is
   that "the write surface has two doors and only one of them is enumerated."
   Correcting the enumeration is the safe half. Making `SUPPORTED` mean
   something different is the other half, and it is an operator's decision.

### What would newly refuse under (a)

- `set_limits` and `attach_senders`: cannot be routed without adding to
  `SUPPORTED`, which is forbidden.
- `create_lead` and `attach_leads`: would need an `Authorization` and a
  `configdiff` Readback. The staging path does not produce either. Adding
  them is possible but is a behaviour change to the staging path.
- `pause_campaign`: already in `SUPPORTED` as `EMAIL_PAUSE` and
  non-prospect-facing, so it could be routed through `perform` with no new
  refusals — it would gain only the `staged_already` idempotency check.
- `set_schedule`, `ensure_custom_variables`, `update_lead`: no operation
  constant exists for these; new constants would need to be defined and
  added to `SUPPORTED` before routing.

## The test

`tests/test_write_surface_enumeration.py` scans both factory files for direct
provider write calls and fails if any call is not in the declared registry.
The registry lives in the test file and must be updated when a new direct call
is added. A developer who adds a `bison.foo()` call to `bisonfactory` without
declaring it here gets a failing test.
