## Question 2: Why did `--limit 20` process 9 records?

### The Code Path

From `src/run.py`:

```python
def run(..., limit=None, ...):
    recs = store.load()
    targets = [r for r in recs if ids is None or r["id"] in ids]
    if limit:
        targets = targets[:limit]
    
    if "enrich" in stages:
        report["enrich"] = stage_enrich(targets, ...)
```

From `src/run.py stage_enrich()`:

```python
def stage_enrich(recs, spend, cap, notes, checkpoint=None):
    budget = enrich.Budget(cap)
    touched = 0
    for rec in recs:
        if not needs(rec, "enrich"):
            continue
        # ... process the record ...
        touched += 1
    return {"records": touched, ...}
```

From `src/run.py needs()`:

```python
def needs(rec, stage):
    if rec.get("state") in TERMINAL:
        return False
    if is_done(rec, stage):
        return False
    return True
```

### The Answer

`--limit 20` slices the **first 20 records** from the queue. The `stage_enrich` function then iterates through those 20 and checks `needs(rec, "enrich")` for each.

`needs()` returns `False` for:
1. Records in terminal states (`dropped`, `pushed`)
2. Records where the enrich stage is already marked `done`

So if only 9 of the first 20 records need enrichment (the other 11 are either terminal or already enriched), only 9 are processed.

**The limit bounds the scan window, not the work done.** This is correct behavior: a limit that silently meant something other than "this many records" would make every bounded run a guess.

### Why This Matters

An operator reading `--limit 20` expects 20 records to be processed. But the actual number processed depends on how many of those 20 need work. This is not a bug; it's the resume mechanism working correctly. A record that was already enriched should not be re-enriched, and a dropped record should not be touched.

However, this means the operator cannot predict exactly how many records will be processed from the limit alone. They must also know the state of the records in the queue.

## Question 3: Why did `drafted` and `verified` move?

### The Code Path

From `src/run.py main()`:

```python
def main(argv=None):
    # ...
    report = run(source=a.source, client=a.client, lane=a.lane, ...)
```

From `src/run.py run()`:

```python
def run(source=None, client=None, lane=None, ...):
    if source:
        ingested = ingest.run(source, client=client, lane=lane)
    
    recs = store.load()
    targets = [r for r in recs if ids is None or r["id"] in ids]
    if limit:
        targets = targets[:limit]
    
    if "enrich" in stages:
        report["enrich"] = stage_enrich(targets, ...)
    if "qualify" in stages:
        report["qualify"] = stage_qualify(targets, ...)
```

### The Answer

**`--lane` does NOT scope the enrich or qualify stages.** The `lane` parameter is only used by `ingest.run()` to filter which records to ingest. Once the records are in the queue, the enrich and qualify stages process **all records** (up to the limit), regardless of lane.

So when Claude ran:
```bash
python -m src.run --spend --cap 0 --stage enrich --stage qualify --lane domains --limit 20
```

The `--lane domains` had no effect on the enrich/qualify stages. The runner:
1. Loaded all 300 records from the queue
2. Took the first 20 (due to `--limit 20`)
3. Ran enrich and qualify on those 20, regardless of their state or lane

### Why `drafted` Fell and `verified` Rose

The runner processed records in various states, including `drafted` and `verified`. Here's what happened:

1. **`drafted` fell from 44 to 37:** Seven records in the `drafted` state were processed by the runner. The enrich/qualify stages may have moved them to other states (e.g., if their contacts changed or their ICP verdict changed).

2. **`verified` rose from 26 to 35:** Nine records were moved to the `verified` state. This happens when `enrich.enrich_record()` finds a sendable email address for a record. With `--cap 0`, no paid person-search was done, but existing contacts may have been re-verified or new free contacts may have been found.

3. **`queued` did not move (stayed at 316):** This is because the runner processed the first 20 records, which were likely not in the `queued` state (they were in other states like `drafted`, `verified`, etc.). The queued records are later in the queue and were not reached by the limit.

### The Design Issue

This is a **design issue**: `--lane` should scope the enrich/qualify stages, but it doesn't. An operator running `--lane domains` expects only domains-lane records to be processed, but the runner processes all records.

This is not a bug in the traditional sense; it's a missing feature. The lane filter is applied at ingest time, not at run time. To fix this, the runner would need to filter `targets` by lane before passing them to the stages.

## Safety Assertion: Can the Free Path Drop Records?

### Analysis from Code

From `src/enrich.py enrich_record()`:
- A record is dropped only when all contacts are excluded/invalid AND the company is rejected by ICP
- With `cap=0`, no paid calls are made, so no new contacts are discovered
- The record keeps its existing contacts (if any)

From `src/qualify.py company()`:
- `qualify.company()` does NOT drop records
- It sets `qualification.verdict.icp_status` but does not change `state`
- The state change to `dropped` happens in `enrich.outcome()`, not `qualify`

From `src/qualify.py _release_stale_icp_drop()`:
- This can UNDROP a record if the ICP rejection no longer stands
- It moves state from `dropped` to `queued`
- This is the safe direction only

### Conclusion

**The free path (enrich + qualify with cap=0) cannot drop records.** 
- `enrich` with `cap=0` does no paid calls, so no new contacts are found that could be excluded
- `qualify` does not drop records; it only sets verdicts
- The only state change is `_release_stale_icp_drop()`, which moves dropped→queued (safe direction)

**SAFE TO RUN over the whole batch.**
