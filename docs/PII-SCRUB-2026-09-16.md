## 2. Cost of Changing the Record-ID Convention

### Where the id is generated

`src/ingest.py:81-83` — the `slug()` function:

```python
def slug(s):
    s = re.sub(r"[^a-z0-9]+", "-", (s or "").lower()).strip("-")
    return s[:40] or "record"
```

Called at `src/ingest.py:187`: `rid = slug(raw_id or company or domain)`.
Also called at `src/web/upload.py:619`: `rid = base = ingest.slug(f"{row['domain']}")`.

### What reads it

442 references to `record_id` across `src/` — every module that touches a
record, a campaign, an event, a lead, or a provider payload. The record ID is
the system's primary key. It appears in:

- **State files**: `work/queue.jsonl` (the `"id"` field of every record),
  `work/campaigns.jsonl` (the `"record_ids"` array of every campaign)
- **Provider payloads**: leads at EmailBison carry `record_id` in
  `customUserFields`; leads at HeyReach carry it in `customVariables`; the
  `record_id` is written at add-lead time and read back at every readback
- **Event log**: every event in `work/events.jsonl` carries `record_id`
- **Documents**: every doc that names a record names its ID
- **Scripts**: task scripts that reference specific records

### What breaks if it becomes a hash

1. **Provider state we cannot rewrite.** Campaign 481 at EmailBison has 23
   leads with `record_id` values in `customUserFields`. Campaign 599020 at
   HeyReach has leads with `record_id` in `customVariables`. These are written
   at the provider and we cannot bulk-update them. A hash change would orphan
   every existing lead: the local queue would say `px-abc123` while EmailBison
   says `adcuratio-com`, and `adapters.from_emailbison` reads `record_id` to
   match leads back to local records (`src/adapters.py:93`).

2. **Event log continuity.** 1,200+ events reference records by their current
   IDs. A hash change breaks the link between historical events and current
   records unless every event is also rewritten — and the event log is append-
   only by design.

3. **Campaign state.** `record_ids` arrays in campaigns.jsonl would need
   rewriting, and every campaign's audit trail references the old IDs.

4. **Documents and scripts.** Every doc that names a record would need
   updating. This is the cheap part — but it is also the part that loses
   human readability. An operator reading `adcuratio-com` knows which company
   it is; `px-a8ca1565fdd1` tells them nothing without a lookup table.

5. **Cross-system correlation.** The record ID is the one value that lets us
   correlate a local record with a provider lead, an event, a signal, and a
   document. Changing it breaks that correlation everywhere it has been
   written, which is every system that has ever touched a prospect.

### The provider side specifically

Leads in campaign 481 carry `record_id` values that we cannot rewrite:

- EmailBison `customUserFields.record_id` — written at lead creation, no bulk
  update API, no delete-and-recreate without losing thread history
- HeyReach `customVariables.record_id` — same constraint; HeyReach has no
  staging state and no bulk update for custom fields on existing leads

The provider-side IDs are the load-bearing reason the convention cannot change
without an operator decision that reaches outside this repository.

## 3. Should the Guard Allowlist Record IDs?

**The guard is right to flag them.** A record ID derived from a prospect's
domain identifies that prospect exactly as well as the domain does.
`adcuratio-com` is `adcuratio.com` with the dot replaced; it is not a
different category of identifier, it is the same identifier in a different
format. Allowlisting it would create a hole the size of the entire queue:
every record ID in every document would be exempt, and the guard would catch
nothing that arrives through the ID convention.

**But the guard cannot go green while the convention stands.** The record IDs
are in RESULT blocks of completed tasks (which this scrub does not touch), in
the task description of TASK-189 itself, and in the queue snapshot. The guard
scans all tracked files; the IDs are in tracked files; the guard fires. This
is correct behaviour, not a bug.

**The answer is an operator decision, not a guard change.** The convention
exists because it was chosen before the guard did, and it reaches provider
state we do not own. Changing it requires:

1. An operator decision that the readability loss is worth the provider-side
   rewrite cost
2. A migration plan for campaign 481 and 599020 leads
3. A decision on whether historical events keep their old IDs or are rewritten
4. Only then, a guard change

Until that decision is made, the guard should continue to flag record IDs as
PII, because they are PII. The correct resolution is to change the convention,
not to exempt it from the detector.

**Note:** this scrub does NOT change the convention. The task explicitly says
"Do not change the record-id convention or the code that generates ids." The
record IDs in the 5 files above that are outside RESULT blocks have been
hashed along with everything else. The record IDs inside RESULT blocks remain.

## 4. The Scrub

### Hash function

```
SHA-256("resonate-pii-salt-2026-09-16" + value)[:12]
```

Prefixed with `px-`. Same input always gives same output. The salt is public
(in this script) and exists only to prevent rainbow-table lookup.

### Implementation

`scripts/task189_scrub_pii.py` — deterministic, reproducible, case-insensitive
replacement. Longest match first (so "brooke baron" replaces before "brooke").
