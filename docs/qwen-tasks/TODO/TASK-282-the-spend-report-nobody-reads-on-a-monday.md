# TASK-282 — the spend report nobody reads on a Monday

## The question this answers

**Does the weekly report the operator actually receives carry what we spent?**

Today it does not. `scripts/spend_report.py` does not exist on master.
TASK-278 built one on a worker branch and it has not been reviewed. A report
that exists and is not in the document nobody reads is the repository's oldest
failure mode: *existence is not function.*

`src/weeklyreportwatch.py` is the schedule — Monday 08:00 Zagreb, 07:30
preview in `#resonate-os` with a stop. `src/clientreport.py` renders sections
from a data dict. The spend figure has to enter through the data dict and
render in a section, and the **07:30 preview must show it** — otherwise the
first time a wrong spend number is seen is after it has gone out, which has
already happened once (the 2026-09-22 14:42 report that told a client 69
domains had no sends on a day those mailboxes sent 494).

## What to build

1. A spend section in the **internal** report template. Spend is our cost, not
   the client's business; it must NOT be in `CLIENT_SAFE_SECTIONS`. Assert
   that in a test.
2. The data dict gains the spend rows by **calling the spend report**, not by
   duplicating its arithmetic. One source of the number.
3. The section renders: per provider, credits used, USD at list, and the
   SOURCE of each figure. A provider with no balance endpoint renders as
   "no endpoint — read at <dashboard path>", never as 0 and never omitted.
4. **The section must survive the report being generated when the spend read
   fails.** A provider timeout renders as UNREAD with the reason and the
   report still goes out; it does not take the Monday report down, and it does
   not print a stale number as a fresh one.
5. The 07:30 preview and the 08:00 post render the **same** section from the
   **same** data dict. Prove it by comparing the two renders, not by reading
   the code.

## The acceptance bar

- `weeklyreportwatch`'s preview payload contains the spend section. A test
  drives the **preview path**, not the renderer.
- Deleting the call that injects spend into the data dict makes at least one
  test fail. If it does not, the test is testing the seam.
- A test asserts the spend section is absent from every client-safe template
  and present in the internal one.
- A test asserts the report **never emits a value from `config.VARIABLES`** —
  carried forward from TASK-278 and it is the rule that matters most here.
- A provider read failure produces UNREAD-with-reason in the rendered output
  and a report that still renders.

## What evidence counts

- The rendered internal report for one workspace, with the spend section
  visible, generated by running the report path — paste the section.
- The **diff of the 07:30 preview render against the 08:00 render**, which
  must be empty for the spend section.
- `grep -rn "spend_report" src/` showing the call site inside the report data
  path, not only the definition. Paste the grep.
- The failure render: the same section with one provider forced to time out.

## WHAT WOULD MAKE THIS A FALSE PASS

- **A test that calls the spend section renderer directly.** Every one of the
  three reviews lost on 2026-09-14 passed exactly that way. Drive it from
  `weeklyreportwatch`'s preview.
- **A second copy of the spend arithmetic** inside `clientreport`. Two
  formulas will diverge and the client-facing one will be the stale one.
- **Numbers from our own ledger presented as provider figures.**
  `work/spend-ledger.jsonl` has not been written since 2026-09-16 and holds
  79 deliverable + 97 reoon rows against 11,417 verification journal rows —
  some 22,000 credits with no ledger row. A report sourced from it is wrong
  by roughly two orders of magnitude on verification. **Say, per row, whether
  the figure came from the provider or from us.**
- **A green suite as the proof.** Render the report and read it as a person.
  A section can be present, wired, tested and still print "$0.00" for every
  provider.
- A section that renders only when a fixture supplies the data. Run it against
  the real read at least once.

## Boundaries

- **No provider writes.** Balance and usage endpoints are reads.
- **Never print a credential value, and never print a whole response.** Print
  NAMED FIELDS ONLY. On 2026-09-24 a session filtered Apify's `/users/me` by
  hand to hide email and user id and printed the account's proxy password in
  full, because it allow-listed what to HIDE instead of naming what to SHOW.
- Credential names come from `config.VARIABLES`. Never guess one; run
  `py -3 scripts/credential_health.py --verify`.
- **Do not post to Slack.** Render locally. A Monday post is the operator's.
